# Poisson Labs Public Repository Hygiene Standard

**Standard:** `docs/repo-hygiene.md`  
**Applies to:** All public repositories published under `github.com/poisson-labs`.  
**Effective:** September 2026  
**Revised:** 2026-09-21. Devlogs live in the vault, never in a repository (section 1.5 withdrawn, new section 2.7 and checklist item 12). History is rewritten only when a repository goes public, and that rewrite is the one force-push the standard allows (checklist items 9 and 10).

This standard defines what a Poisson Labs public repository must contain and what it must never contain. It ensures that every public codebase is immediately reproducible, honest about its scope, legally sound, and free of internal agent tooling artifacts or personal data.

---

## 1. What a Public Repository Must Contain

Every public Poisson Labs repository must contain the following:

### 1.1 Contextual, Reader-Facing `README.md`
A reader arriving from a published post, paper, or artifact must understand immediately what the repository is and how to run it.
- **Context & Post Link:** Explicit link to the published article or technical report on `poissonlabs.ai` that cites the repository.
- **What Was Measured:** Clear description of the experimental substrate, model versions, perturbation axes, and evaluation protocol.
- **What Was Found:** Concrete summary of empirical findings. Every reported number must be verifiable against committed structured artifacts (`post_numbers.md`, CSV summaries, or raw shards), with explicit citations beside each figure.
- **What the Study Could Not Detect:** Honest accounting of methodological boundaries, unmeasured failure modes, metric validity limits, or scope restrictions.
- **Reproduction Steps:** Step-by-step instructions to create the environment, run verification sanity checks, execute analysis scripts, and reproduce all figures and tables from committed data or from scratch.
- **Direct Artifact Links:** Clickable links to primary figures (SVG, PDF, PNG) and data tables in the repository.
- **Citation:** Standard BibTeX entry attributing Poisson Labs.

### 1.2 `LICENSE`
An explicit permissive open-source license file at the repository root, standardly MIT:
```text
Copyright (c) 2026 Taylor Kolasinski / Poisson Labs
```

### 1.3 `NOTICE`
A standalone `NOTICE` file documenting all third-party code, foundation model weights, benchmark datasets, and library dependencies.
- Every license grant must be quoted from the upstream source file or official terms page, with the exact URL cited.
- If a dataset or model does not have a formal license file or if commercial terms are unverified, state this explicitly in the `NOTICE` rather than asserting unverified permissions.

### 1.4 Authoritative Project Metadata (`pyproject.toml`)
- Canonical contact email: `work@poissonlabs.ai`.
- Repository URLs pointing to `https://github.com/poisson-labs/<repo>`.
- Explicit dependency floors for all runtime and development packages.
- Configured linter and test suite runners (`ruff`, `pytest`).

### 1.5 (Withdrawn 2026-09-21)
A repository no longer carries a study log. Devlogs live in the vault only; see section 2.7. The number is kept so that earlier citations of this standard still resolve.

### 1.6 Reproducible Analysis & Verified Run Data
- Scripts that extract published figures and metrics from raw data must be deterministic, self-contained, and output relative paths.
- Analysis notebooks must execute cleanly top-to-bottom.
- Raw run data (such as Parquet shards, logs, and run manifests) that are intentional and load-bearing for the study must be documented, checksummed, and tracked.

## 2. What a Public Repository Must Never Contain

A Poisson Labs public repository must never contain the following:

### 2.1 Internal Agent Tooling and Workflow Files
- **No Agent Task Manifests:** Remove files such as `coding_agent_requests.md`, `CLAUDE.md`, `.agents/`, or internal scratchpads.
- **No AI Attribution in Commits:** Git commit messages must be plain, human-authored descriptions of changes. Never include `Co-Authored-By: Claude...`, "generated by AI", or automated agent signatures.
- **No Tooling References in Narrative Text:** Docs and any other narrative file in the repository must describe what was built or discovered, not which tooling or agent performed the task.

### 2.2 Hardcoded Absolute Local Paths
- No paths containing `/Users/<user>/...`, `/home/<user>/...`, or local worktree roots.
- All code, scripts, and notebook outputs must use repository-relative paths (`Path(__file__).resolve().parent...`).
- Stored notebook outputs must be clean: diagnostic prints that dump local paths must have their outputs cleared. Actual empirical study evidence in notebook outputs must be kept, with any local paths scrubbed to relative paths.

### 2.3 Stale, Defunct, or Personal Email Addresses
- No personal Gmails or legacy company domain emails (e.g. `flowmode.co`) in `pyproject.toml`, documentation, git commits, or manifests. Use `work@poissonlabs.ai` in metadata, documentation, and manifests; git commits carry the author address in checklist item 10.

### 2.4 Secrets, Credentials, and Machine Tokens
- Never commit API keys, cloud tokens, private keys, authentication cookies, or internal server tokens.

### 2.5 Ephemeral and Generated Cache Files
- No Python bytecode (`__pycache__`, `*.pyc`), virtual environments (`.venv`), coverage files (`.coverage`), pytest caches (`.pytest_cache`), OS metadata (`.DS_Store`), or IDE configs (`.vscode`, `.idea`).
- Ensure `.gitignore` explicitly prevents accidental re-introduction.

### 2.6 Orphaned or Unverified Floating Files
- Every tracked file must belong to one of: source code, tests, documentation, canonical analysis, verified figures, or load-bearing run data.
- Scratch exploration scripts, one-off test dumps, or unreviewed files must be resolved and removed prior to public release.

### 2.7 Devlogs
- A devlog never lives in a repository. Devlogs live in the vault only.
- Every Poisson Labs repository, public or not yet public, lists `devlog.md` in its `.gitignore`, so one cannot be committed by accident.

## 3. Pre-Release Audit Checklist

Before releasing any Poisson Labs repository to public visibility:
1. [ ] `docs/repo-hygiene.md` is present and verified.
2. [ ] `README.md` is reader-facing, explains findings with source citations, and links to the live post.
3. [ ] `LICENSE` is present with Poisson Labs copyright.
4. [ ] `NOTICE` quotes upstream licenses, citations, and dataset terms with URLs.
5. [ ] `pyproject.toml` author email is `work@poissonlabs.ai`.
6. [ ] All absolute local paths in code and notebook outputs are eliminated or scrubbed.
7. [ ] All agent request files and tooling traces are purged.
8. [ ] Working tree is clean; load-bearing run data is verified; all uncommitted study files are resolved.
9. [ ] Git commit history is reviewed: plain commit messages, zero AI attribution. No force-pushes, with one exception: the history rewrite in item 10, when the repository goes public. That is the only force-push this standard allows.
10. [ ] Author identity is the work identity: commits are authored as `TaylorKolasinski` with `taylor@poissonlabs.ai`, as author and as committer (a commit GitHub itself makes keeps GitHub as committer). That address and the personal one are both verified on the one GitHub account, so no second account is involved. History is rewritten only when a repository goes public, and only then: the rewrite gives every commit the work address, and it is the one case in which a force-push is allowed (item 9). A repository staying private is not rewritten. A rewrite moves every commit hash, so the vault, the board, and any notes citing those hashes need re-pointing afterwards.
11. [ ] Commits are signed, so GitHub shows them as verified rather than unverified. The signing key is registered on the GitHub account as a signing key; a key registered only for authentication still shows every commit as unverified. For a repo going public, the history rewrite resigns the existing commits in the same pass.
12. [ ] `.gitignore` includes `devlog.md`, and no devlog is tracked. Devlogs live in the vault only (section 2.7).
